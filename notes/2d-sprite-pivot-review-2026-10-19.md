# 2D 스프라이트 그래픽 개편 검토

2026-10-19 · 결정 사항: **2D 스프라이트 기반으로 전환 검토** — 전환 동기:
AI 주민이 발명한 아이템·건축물을 AI가 그래픽으로 생성해야 하는데 3D 에셋
생성은 비현실적.

> **⚠️ 2026-10-19 정정(사용자 지시)** — 그래픽 기준은 레퍼런스 이미지(핸드페인트
> cozy)가 아니라 **원본 앱 `../terrafolk`(웹 FE)의 2D 도트(픽셀) 룩**이다.
> 정투형(top-down) 타일·LPC 픽셀 주민·픽셀 프롭 체계를 원점으로 유지·진화한다.
> 레퍼런스 이미지·"SCR 느낌"은 방향 참고(밀도·가독성)일 뿐 스타일 목표가 아니다.
> 메모리 `original-fe-2d-dot-baseline` 참조. 아래 §2의 핸드페인트 스펙은
> 폐기하지 않고 "후기 업스케일 방향 후보"로만 남긴다.

## 1. 결론 (요약)

| 질문 | 판정 |
|---|---|
| 3D 에셋 AI 생성 | **비추천** — 메시·토폴로지는 차치해도 리깅+애니메이션이 결정적 병목. 이 repo가 GLB 스키닝(×100 정규화 사건)으로 이미 입증한 비용 |
| 2D 스프라이트 + 이미지 생성 | **추천** — 아이콘·건축·소품(정적 스프라이트)은 2026년 이미지 생성 모델의 가장 성숙한 영역. 파이프라인 구축 가능 |
| SCR 리마스터 "느낌" | 레퍼런스 이미지 판독 결과 실제 타깃은 **SCR(군사 SF)이 아니라 핸드페인트 프리렌더 아이소메트릭**(cozy farm-builder 톤). SCR에서 가져올 것은 "프리렌더 고밀도 스프라이트 + 아이소 관전 가독성"이라는 방식 자체 |
| 북극성(주민 생명감) 영향 | 치비 비율+따뜻한 톤+말풍선 = 감정 전달에 유리. 애님 품질은 "3D→베이크"로 보존(§4-B). 리스크는 착용 표현(§6) |

캐릭터 디자인 선택서(2026-10-18 노트)와의 관계: 레퍼런스 이미지는
**1-C 치비** 방향과 정합(2~3두신) — 스타일 질문은 사실상 이 레퍼런스로
확정된 것으로 봄. 1-E(3D 씬에 빌보드)는 아니고, 월드 자체를 2D로 간다.

## 2. 레퍼런스 이미지 스타일 분해 (재현 스펙)

이미지 판독(analyze_image) 결과, 재현에 필요한 속성:

- **렌더링**: 3D 프리렌더 베이스 + 핸드페인티드(수채/구아슈 붓터치) 텍스처
  오버레이. 픽셀아트 아님, 순수 2D 드로잉 아님
- **시점**: 아이소메트릭(약 30° 디다운), 정면 향함, 캐릭터는 8방향 후보
- **캐릭터**: 치비 2~3두신, 무거운 외곽선 아님(부드러운 에지), 과장된 도구
- **팔레트**: 고채도·중명도, 따뜻한 갈색·초록 지배 + 포인트 컬러, 검정
  그림자보다 채도 낮춘 그림자
- **라이팅**: 좌상단 소프트 라이트 + 통일된 앰비언트 오클루전, 스프라이트에
  조명 베이크(SCR 방식과 동일 — 런타임 동적 조명 없음, day/night는 전역
  컬러 그레이딩으로)
- **AI 생성 적합성**: 핸드페인트 cozy 아이소는 확산 모델 학습 데이터가
  풍부한 영역 — 스타일 잠금이 가장 잘 되는 장르 중 하나. SCR 다크 SF보다
  생성 친화적

## 3. AI 발명품 그래픽 생성 파이프라인 (전환의 핵심 동机)

### 분담 (repo 역할 규칙 준수)

- **백엔드(`../terrafolk`)**: 생성·검수·저장 전부. LLM 호출과 동일 위치
- **이 repo(클라이언트)**: 플레이스홀더 → 원격 스프라이트 스트리밍 → 캐시·적용

### 파이프라인 (create-game-assets 규율 적용)

1. **트리거**: 발명 이벤트(룸 worldboot). 기존 계약의 `icon({tpl,primary,accent})`
   템플릿 아이콘을 **즉시 표시(플레이스홀더 계층)** — 생성은 비동기
2. **생성**: 스타일 바이블(§2 스펙)을 고정 프롬프트 블록(ROLE/SUBJECT/VIEW/
   ART DIRECTION/GAME-SCALE READ/LOCKS/EXCLUDE) + 레퍼런스 이미지 스타일
   참조(img2img/IP-Adapter류)로 잠금. 발명 = 세계에 없는 조합("돌칼날 정미소")
   이라 텍스트→이미지가 잘 맞음
3. **검수 게이트(자동)**: 알파 채널 실측(투명 보장 안 됨 — rembg류 배경
   제거 후 검증), 해상드 통일(512 등), 크롭·피벗 정렬, 색 히스토그램으로
   스타일 편차 검사(레퍼런스 팔레트 거리), 텍스트 렌더·모의 프레임 검출
   리젝트. `asset_report.py` 방식의 머신 리더블 리포트
4. **저장·계약**: CDN은 assets.suseona.com(이미 운영 중 — 레퍼런스 URL이
   그 도메인) 사용. 계약(`data-contract.md` §17.82) `relic/invention`에
   `sprite_url`, `gen:{model, seed, style_ver}` 출처 필드 추가
   (provenance 기록 의무)
5. **클라이언트 적용**: 이 repo는 스프라이트 다운로드+캐시(안드로이드 캐시
   경로)+적용만. 웹 FE는 DOM이라 동일 URL 그대로

### 생성 난이도별 단계

| 대상 | 난이도 | 비고 |
|---|---|---|
| UI 아이콘 | 즉시 가능 | 템플릿 아이콘 대체 업그레이드 |
| 건축물 스프라이트(정적 1~3 상태) | 가능 | 가장 큰 관전 임팩트 |
| 소품·떨어진 아이템 | 가능 | |
| 소지·착용품(캐릭터 부착) | 어려움 | 방향별 필요 — 1차는 아이콘+인벤토리로 한정 |
| 생물 | 보류 | |

## 4. 주민(캐릭터) 파이프라인 — 2D 전환의 최대 난점

순수 이미지 생성으로 방향×프레임 일관 애님은 불가능에 가깝다. 세 가지 경로:

- **4-A. LPC 부품 합성(웹 FE 자산 재사용)** — walk/idle/sit/slash 시트가
  이미 존재, look JSON 계약 그대로. **1차 MVP 추천**: 월드 2D 전환을 먼저
  검증하는 수단. 단 픽셀아트라 레퍼런스 핸드페인트 톤과 불일치 — 임시
- **4-B. 치비 3D → 프리렌더 베이크(SCR·레퍼런스 방식, 최종 추천)** —
  CC0 치비 GLB(Kaylousberg/Kenney)를 헤드리스 렌더로 방향×프레임 베이크
  → 색 보정·필터로 핸드페인트 톤 통합. 애님 품질 보존, 착용은 베이크
  시점 합성(§6). 용량 대략: 128px 프레임 × 8방향 × ~200프레임 ≈ 종족당
  수 MB(KTX2 압축 시) — 팔레트 스왑(colormap 개념 이식)으로 변형 확장
- **4-C. 순수 2D 수제/생성** — idle 정도만 가능, 애님 커버 불가. 비추천

권장: **A로 시작해 B로 마무리**(A의 LPC 애님 재생기가 B의 시트 포맷을
그대로 재사용하도록 포맷을 먼저 확정).

## 5. 이 repo 마이그레이션 영향

- **재작성 대상(`src/world/`, ~5,700줄)**: terrain·splat·water·wind·precip·
  sky·daynight·models·wear·outfit·outline·occlusion → 2D 렌더러로 교체.
  Camera2d + **스프라이트 자체에 iso 투영이 박힌 구조**(진짜 기울임 3D
  카메라 아님 — SCR이 이 방식) + y-sort. pick은 스크린스페이스로 단순화.
  day/night·시간대 틴트는 풀스크린 컬러 그레이딩으로 이식
- **지형**: 데모 월드는 고정 시드(20261011) 정적 — 현재 3D 씬을 1회
  상향 베이크한 대형 이미지(또는 청크)로 시작 가능. 라이브/신규 월드는
  타일셋 스펙 필요
- **유지되는 것**: `src/platform/`(게임 무관), `src/ui/`(bevy_ui 단일
  구현 원칙 그대로), net/apply·좌표계, ws-link·colyseus-lite
- **⚠️ 진행 중 작업 충돌**: 작업 트리에 WGSL→WESL 셰이더 전환이 진행 중
  (water/splat/wind/precip .wesl). 2D 전환 시 해당 셰이더 대부분이 무의해짐
  — 이 검토를 채택하면 그 작업은 중단·정리 결정 필요
- **성능(반대급부, 안드로이드 우선 원칙에 부합)**: 스키닝 CPU 비용 소멸
  (직전 커밋의 "화면 밖 애님 스로틀"류 최적화 불필요화), 드로우콜은
  아틀라스 배칭. APK 에셋 주입 파이프라인은 스프라이트 시트로 동일하게

## 6. 리스크

1. **스타일 드리프트**: 수백 개 생성 에셋의 일관성 — 스타일 바이블+시드+
   레퍼런스 고정 없이는 불가능. 히어로 에셋 1개 승인 → 패밀리 생성 순서
   (create-game-assets 5~6단계) 준수
2. **착용 시스템 재설계**: 본 앵커 3D 부착 → 2D 레이어 합성(방향별 스프라이트
   오버레이). 기존 검증값·오프셋은 무효 — 4-B 베이크 시점에 통합하는 편이
   합리적
3. **생성 지연·실패**: 플레이스홀더(템플릿 아이콘) 필수 — 계약에 이미 있음
4. **줌 인 한계**: 프리렌더 스프라이트는 해상도 상한 — 베이크 해상도를
   관전 줌 최대 배율에 맞춰 결정(128px vs 256px 프레임)

## 7. 권장 로드맵

1. **스타일 바이블 + 시드 에셋 승인** — 레퍼런스 기반 프롬프트 블록 확정,
   히어로 에셋(건축 1·아이콘 1) 생성 → 게임 스케일 검증 (백엔드 협조)
2. **월드 2D 렌더러 프로토타입**(이 repo) — Camera2d + y-sort + 베이크
   지형 + LPC 임시 주민. 데모 월드로 관전 플로우 패리티 확인
3. **발명품 생성 파이프라인 연결** — 계약 확장(sprite_url·provenance) +
   클라이언트 스트리밍·캐시
4. **치비 베이크 주민 교체(4-B)** + 착용 레이어 합성
5. 웹 FE도 동일 생성 에셋 공유(에셋 단일 원천 — assets.suseona.com)
